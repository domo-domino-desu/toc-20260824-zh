Turing machines input strings and output strings, sequences of tape symbols.
So a natural way to work is to represent problems as strings,
put them on the tape, run a Turing machine on them, and end with
solutions as strings.

Everyday computers work the same way.
We might imagine a program that finds  the shortest driving distance
between cities that  
works with a map of the country idalized as a graph,
a collection of nodes and edges, intersections and the roads joining them.
The program's input would be that
we encode that graph as a strings of symbols,
and likewise for the output. 



\section{Strings}
An algorithm must accept a variety of inputs.
For instance, a shortest-path algorithm might accept any
graph that is formatted in a certain way (perhaps an ordered pair of nodes
first, represented as integers, 
and then edges represented as pairs of nodes).
Thus inputs come from a set of strings, which satisfy some conditions.

\subsection{Definition}
This section uses familiar terms, and the definition of
each is related to its informal meaning,
but the technical meanings have aspects that may be surprising.

\begin{definition}
A \definend{symbol} (or \definend{token}) is something that 
a machine can read and write.\footnotemark{}  %
An \definend{alphabet} is a set of symbols.
\end{definition}
\footnotetext{We can imagine Turing's clerk 
doing a calculation without symbols, keeping track of information by 
\protect\citetext{requiring elephants to move 
to the left side of a road or to the right}{Less fancifully, we could be making
a Turing machine out of Legos and want to keep track by sliding a block
from one side of a column to the other.
Or, we could be using an abacus.}.
But 
\protect\citetext{we could translate any such procedure}{While a 
person may quite sensibly worry that elephants could be not just on
the left side or the right, but in any of the continuum of points
in between, 
we will make this 
assertion without more philosophical analysis than by just referring
to the discrete nature of our mechanisms
(as Turing basically did).
That is, we take it as an axiom.} 
into one using marks that our mechanism's read/write head can handle with 
a tape, such as \protect\str{0} and \protect\str{1}.
So the restriction to readability and writeability is not essential.
We include it in the definition of symbols because our mechanisms will need to 
read and write them, and for this purpose elephants
would be inconvenient.}

We write symbols in a distinct typeface, as in \str{1} or \str{a},
because the alternative of quoting them would be 
clunky.\footnote[2]{We need to do something because
in traditional mathematical work, in an expression such as
``let $S=\protect\set{a,b}$'' the $a$ and $b$ are variables,
taking on values from some domain.
But symbols are not variables, they don't hold a value.
They are themselves the value.}
The term ``symbol'' is potentially misleading in that some 
symbols contain more than one character.
For instance, a programming language
may have \str{if} as a symbol, as indecomposable
into two separate letters.

Traditionally to denote an alphabet we use $\Sigma$.
An alphabet can be finite $\Sigma_0=\set{\str{a},\dots, \str{z}}$ 
\citetext{or infinite $\Sigma_1=\set{\str{0},\str{1},\ldots}$}{%
There is no point in having an uncountably infinite alphabet as
the machines we use will run for at most countably many steps
and so use at most countably many symbols.}.

\begin{definition}
A \definend{string} (or \definend{word})
over an alphabet is a finite sequence of elements from that alphabet.
The string with no elements is 
the \citetext{\definend{empty string}, deonted ~$\emptystring$}{Possibly 
  $\emptystring$ was chosen as an abbreviation for `empty'.   
  Some authors use $\lambda$, possibly from the German word for 
  `empty', \textit{leer}.  \autocite{csse:Siren}}.
\end{definition}

We denote strings with lower case Greek letters 
and often denote the string's 
elements with the associated lower case roman letter, as in
$\sigma=\sequence{s_0,\ldots,s_{i-1}}$
or $\tau=\sequence{t_0,\ldots,t_{j-1}}$.\footnote{If $i=0$ or 
$j=0$ then this gives the empty string, so $i,j\in\N$.}

We use strings a lot. 
Sticking with diamond brackets and commas would be clunky. 
We will often take the shortcut of having
the alphabet consist of single-character symbols and then write strings
by omitting the brackets and commas.
Thus, instead of $\sequence{\str{a},\str{b},\str{c}}$
we may write \str{abc}.\footnote{We want these alphabets to have 
  single-character symbols because for some alphabets with 
  multiple character symbols such as  
  $\Sigma=\set{\str{a}, \str{aa}}$, omitting commas makes some
  strings ambiguous.
  For example, the string \str{aaa} could
  mean $\sequence{\str{a},\str{aa}}$, or 
  $\sequence{\str{aa},\str{a}}$, or
  $\sequence{\str{a},\str{a}, \str{a}}$.} 
However, this convenience 
comes with the disadvantage that without the diamond brackets  
the empty string is just nothing, which is why 
we have the separate symbol~$\emptystring$.\footnote{Omitting the 
diamond brackets and commas blurs the distinction between a symbol 
and a one-symbol string, between \str{c} and $\sequence{\str{c}}$.
However, this is convenient so we accept this disadvantage.}

\begin{example}
The Scheme alphabet contains the symbols \str{or} and \str{car}, and
allows variable names such as \str{a}, \str{x}, or \str{lastname}.
An example of a string is $\str{(or a ready)}$.
This is a sequence of the five alphabet elements:
\str{(}, \str{or}, \str{a}, \str{ready},~\str{)}.
% Scheme writes the sequence by separating its elements with spaces

\end{example}

Strings over the alphabet
$\set{\str{0},\str{1}}$
are \definend{bit strings}.
This alphabet occurs so frequently that we shall set aside a name 
$\B=\set{\str{0},\str{1}}$.% \footnote{We also use $\protect\B$ for the
% set $\protect\set{\protect\true,\protect\false}$, but of course never
% at the same time.}

\begin{example}
A bit string has \definend{even parity} if it has an even number of \str{1}'s
and \definend{odd parity} otherwise.
Some even parity bit strings are 
$\str{11}$, $\str{011}$, $\str{00}$, and $\emptystring$.
\end{example}

\begin{definition}
Let~$\Sigma$ be an alphabet.
Then where $k\in\N$, \definend{$\Sigma^k$}
is the set of length~$k$ strings over that alphabet.  
The \definend{Kleene star $\kleenestar{\Sigma}$}
is the set of all strings over $\Sigma$, of any length,
so $\kleenestar{\Sigma}=\cup_{k\in\N}\Sigma^k$.
\end{definition}

\begin{definition}[Operations on strings] \label{def:StringOps}
Let $\sigma=\sequence{s_0\ldots,s_{i-1}}$ and 
$\tau=\sequence{t_0,\ldots,t_{j-1}}$ be strings.
The \definend{length of a string $\lh{\sigma}$} 
is the number of symbols in that string, 
so that $\lh{\sequence{s_0,\ldots,s_{n-1}}}=n$ 
and the length of the empty string is $\lh{\emptystring}=0$.

The 
\definend{concatenation $\sigma\concat\tau$} of two strings (sometimes
instead denoted 
by abutting the two $\sigma\tau$) 
appends the second sequence to the first
$\sigma\concat\tau=\sequence{s_0\ldots,s_{i-1},t_0,\ldots,t_{j-1}}$.

\label{def:substring}
If 
$\sigma=\tau_0\concat \cdots \concat\tau_{k-1}$ then we may say
that $\sigma$ \definend{decomposes} into the others.
Each $\tau_i$ is a \definend{substring} of $\sigma$.
The first, $\tau_0$, is a \definend{prefix} of~$\sigma$,
and the last, $\tau_{k-1}$, is a \definend{suffix}. 

The \definend{replication $\sigma^n$} of a string is the 
iterated concatenation with itself, so that $\sigma^2=\sigma\concat\sigma$ 
and $\sigma^3=\sigma\concat\sigma\concat\sigma$, etc.
We write $\sigma^1=\sigma$ and $\sigma^0=\emptystring$.

The \definend{reversal $\reversal{\sigma}$} of a string takes the symbols 
in reverse order
$\reversal{\sigma}=\sequence{s_{i-1}, \ldots, s_0}$.
The reversal of the empty string is itself
$\reversal{\emptystring}=\emptystring$.
\end{definition}

(We have used some of that notation already
but we state it formally here, as a reference definition.)

\begin{definition}
A \definend{language~$\lang{L}$ over an alphabet~$\Sigma$}
is a set of strings drawn from that alphabet, 
$\lang{L}\subseteq\kleenestar{\Sigma}$.  
\end{definition}

\begin{example}
Let $\Sigma=\set{\str{a}, \str{b}}$.
The language consisting of strings where the number of \str{a}'s is twice 
the number of \str{b}'s is
$\lang{L}=\set{\emptystring,\str{aab},\str{aba},\str{baa},
               \str{aaaabb}, \,\ldots}$.  
\end{example}

\begin{example}
Let $\Sigma=\set{\str{a},\, \str{b},\, \str{c}}$.
The language of length-two strings over that alphabet is
$\lang{L}=\Sigma^2=\set{\str{aa},\,\str{ab},\,\dots,\,\str{cc}}$.
Over the same alphabet 
this is the language of length-three strings that are sorted in ascending order.
\begin{equation*}
  \set{\str{aaa},\, \str{aab},\, \str{aac},\, \str{abb},\, \str{abc},
    \str{acc},\,\str{bbb},\,\str{bbc},\, \str{bcc},\, \str{ccc}}
\end{equation*}
\end{example}

\begin{example}
The set of bit strings, 
strings over the alphabet~$\B=\set{\str{0},\str{1}}$, 
that begin with \str{1} is 
$\set{\str{1},\,\str{10},\,\str{11},\,\str{100},\,\ldots}$.   
\end{example}

\begin{example}
Another language over $\B$
is the \citetext{finite set
$\set{\str{1000001},\str{1100001}}$}{%
The language is not 
without sense since \str{1000001} represents capital A in the 
ASCII encoding, while \str{1100001} is lower case a.
The American Standard Code for Information Interchange, ASCII,
is a widely used way of encoding character information in computers.  
The most common modern character encoding is UTF-8, 
which is a superset of ASCII.}.
\end{example}

\begin{example}
Let $\Sigma=\set{\str{a}, \str{b}, \str{c}}$.
Recall that Pythagorean triples $\sequence{i,j,k}\in\N^3$ 
are those where $i^2+j^2=k^2$.
A few such triples are $\sequence{3,4,5}$, $\sequence{5,12,13}$,
and $\sequence{8,15,17}$.
One way to describe Pythaorean triples that we will later find convenient
is with this language.
\begin{align*}
  \lang{L}
   &= \set{\str{a}^i\str{b}^j\str{c}^k\in\kleenestar{\Sigma} 
            \suchthat \text{$i,j,k\in\N$ and $i^2+j^2=k^2$}}  \\
   &=\set{\str{aaabbbbccccc}=\str{a}^3\str{b}^4\str{c}^5,\,
            \str{a}^5\str{b}^{12}\str{c}^{13},\,
            \str{a}^8\str{b}^{15}\str{c}^{17},\,\ldots}
\end{align*}
\end{example}

An explanation of the term `language' is that we could take 
the English language to be strings made by concatenating words 
from a dictionary for English.
Here the dictionary is~$\Sigma$, 
and the set of strings over it is
$\lang{L}\subseteq\kleenestar{\Sigma}$.
This highlights that according to the definition, a language can be 
any set of strings at all.
But most of the languages that we 
use are determined by some rules.
We will study such rule sets, grammars, later in this chapter.

Having defined languages, we naturally next consider 
their operations.
Because they are sets, the operations of union, intersection, etc., work
for languages.
However, for instance the union of a 
language over~$\kleenestar{\set{\str{a}}}$ with
a language over~$\kleenestar{\set{\str{b}}}$ 
will be an awkward marriage, a combination of strings of \str{a}'s and 
strings of \str{b}'s.
That is, the union of a language over $\Sigma_0$ with 
a language over $\Sigma_1$ is a language over $\Sigma_0\cup\Sigma_1$.
Of course, if the two alphabets are the same then this accounting
tedium vanishes.
A similar thing happens for intersection; see 
\cref{exer:LanguageUnionIntersection}.

Other operations on languages are extensions of operations on strings.
We define the concatenation of languages 
to be the language of concatenations, etc.

\begin{definition}[Operations on languages]
The \definend{concatenation $\lang{L}_0\concat\lang{L}_1$} of languages is
the set of concatenations
$\set{\sigma_0\concat\sigma_1\suchthat \text{$\sigma_0\in\lang{L}_0$ and $\sigma_1\in\lang{L}_1$}}$.
Sometime in place of $\lang{L}_0\concat\lang{L}_1$ 
we write $\lang{L}_0\lang{L}_1$.

The \definend{$k$-th power of a language $\lang{L}^k$} 
is the language consisting of the
concatenation of $k$-many strings
$\set{\sigma_0\concat\cdots\concat\sigma_{k-1}\suchthat \sigma_i\in\lang{L}}$.
The \definend{Kleene star of a language $\kleenestar{\lang{L}}$} is the 
language consisting of the concatenation of any number of strings.
\begin{equation*}
\kleenestar{\lang{L}}=\set{\sigma_0\concat\cdots\concat\sigma_{i-1}\suchthat \text{$i\in\N$ and $\sigma_0,\ldots,\sigma_{i-1}\in\lang{L}$}}
\end{equation*}
This includes the concatenation of $i=0$-many strings, 
so that $\emptystring\in\kleenestar{\lang{L}}$. 

The \definend{reversal $\reversal{\lang{L}}$} of a language~$\lang{L}$ is 
the language 
$\set{\reversal{\sigma}\suchthat \sigma\in\lang{L}}$.
\end{definition}

\begin{example}
Where the language 
is the set of bit strings $\lang{L}=\set{\str{1000001},\str{1100001}}$ 
then the reversal is $\reversal{\lang{L}}=\set{\str{1000001},\str{10000011}}$.
\end{example}

\begin{example}
If the language $\lang{L}$ consists of two strings $\set{\str{a},\,\str{bc}}$
then $\lang{L}^2=\set{\str{aa},\,\str{abc},\,\str{bca},\,\str{bcbc}}$.
The Kleene star is this.
\begin{equation*}
  \kleenestar{\lang{L}}=\set{\emptystring,\,\str{a},\,\str{bc},\,\str{aa},\,\str{abc},\,\str{bca},\,\str{bcbc},\,\str{aaa},\,\ldots}  
\end{equation*}
\end{example}

Earlier in this subsection we defined 
that the Kleene star of an alphabet~$\Sigma$ is the set of strings
over that alphabet, of any length.
If we consider each character in the alphabet as a length-one string
then we get that this is the Kleene star of the the language. 

One final note, about Kleene star.
This operation is to repeat choosing strings from the language.
We have two ways to go:
we could choose a string~$\sigma$ from the language and then replicate,
getting the set of $\sigma^k$''s.
Or we could repeat choosing strings from the language, getting
$\sigma_0\concat\sigma_i\concat\cdots\concat\sigma_{i-1}$'s.
This second case is more useful and so that's what the definition of
$\kleenestar{\lang{L}}$ calls for.

\begin{exercise}
A string $\alpha$ 
is a \definend{palindrome} if it equals its own reversal
$\reversal{\alpha}=\alpha$.
Show that if $\beta$ is a string then 
$\beta\concat\reversal{\beta}$ is a palindrome.
Do all palindromes have that form?  
\begin{answer}
If $\beta=\sequence{b_0,\ldots,b_{i-1}}$ is a string then 
$\beta\concat\reversal{\beta}
  =\sequence{b_0,\ldots,b_{i-1}}\concat\sequence{b_{i-1},\ldots,b_0}$.

There are palindromes not of that form.
One is $\gamma=\str{010}$, which
cannot be decomposed as $\gamma=\beta\concat\reversal{\beta}$.  
\end{answer}
\end{exercise}

\end{answer}
\end{exercise}

\end{answer}
\end{exercise}

\section{Grammars}
Our formal definition of a language is that it is a set of strings.
This allows for any willy-nilly set.
But often in practice 
\citetext{a language is given by rules}{%
At the start of the 20th century, linguists started trying to formalize 
the description of language, including phrase structure.
Meanwhile, string rewriting rules as formal, abstract systems were introduced 
and studied by mathematicians such as Axel Thue in 1914, 
Emil Post from the 1920's through the 1940's and Turing in 1936. 
Notably, Noam Chomsky, while teaching linguistics to students of 
information theory at MIT, combined linguistics and mathematics by 
taking Thue's formalism as the basis for the description of the syntax of 
natural language.  \autocite{wiki:Linguistics}}.

Here is an example.
To a native English speaker the noun phrase ``the big red barn'' sounds fine
but \citetext{``the red big barn'' sounds wrong.}{Experts 
vary on the exact rules but one source gives 
(article) + number + judgement/attitude + size, length, height + age + 
color + origin + material + purpose + (noun), so that
``big red barn'' is size + color + noun.
This is the Royal Order of Adjectives; 
see \protect\url{http://english.stackexchange.com/a/1159}.}
That is, sentences in natural languages are constructed 
in patterns.
A grammar is an analysis of the structure of a language, a set of rules.

An artificial language can have a grammar also.
For instance, programming languages have very strict syntax rules, 
and the languages we use to express problems will also follow patterns.

In a phrase, 
\citetext{grammars are the language of languages.}{Matt Swift \protect\url{http://matt.might.net/articles/grammars-bnf-ebnf/}} 


\subsection{Productions and derivations}
\begin{example}
Here is a small subset of the rules for for English.
\begin{parenum} 
\item A sentence can be made with a noun phrase followed by a verb phrase.
\item A noun phrase can be made from an article followed by a noun.
\item A noun phrase can also be made from an article, then an adjective, then a 
  noun.
\item A verb phrase can be made with a verb followed by a noun phrase.
\item One article is `the'.
\item An adjective is `young'.
\item A verb is `caught'.
\item Two nouns are `man' and `ball'.
\end{parenum}

We can restate those rules in a convenient notation.
\begin{grammar}
<sentence> \produces{} <noun phrase> <verb phrase>

<noun phrase> \produces{} <article> <noun>

<noun phrase> \produces{} <article> <adjective><noun>

<verb phrase> \produces{} <verb> <noun phrase>

<article> \produces{} "the"

<adjective> \produces{} "young"

<verb> \produces{} "caught"

<noun> \produces{} "man"|"ball"
\end{grammar}
That is a set of \definend{productions} or \definend{rewrite rules}.
Each rule has a \definend{head} on the left, then an arrow, 
then a \definend{body} on the right.
Read the arrow as ``may produce,'' or ``may expand to,'' 
or ``may be constructed as.''

We refer to a rule by its head, so we may say ``sentence's rule.'' 
There are two rules with the head \syntax{<noun phrase>} 
but this won't cause trouble as we won't see any grammars with so many rules
that we need a better naming scheme.
There are also two rules with the head \syntax{<noun>} but 
we have combined 
the two bodies with the `\syntax{|}'~pipe symbol, read aloud as ``or.''

Heads and bodies have two kinds of components.
The kind written in typewriter type, such as `\syntax{the}', 
are elements of the alphabet of the language\Dash they
will appear in strings in the language.
In grammars they are \definend{terminals}.  
Components of the form \syntax{<\,\ldots>}, with angle brackets and in italics, 
are \definend{nonterminals}.
They are category names, or variables, and are
used for intermediate steps in string construction.

{\setlength{\productionpadding}{0em} %temp drop extra padding around symbols
The two symbols \mbox{`\produces'} and \mbox{`\syntax{|}'} are neither 
terminals nor nonterminals,
but are instead part of the syntax of the rules.
These are \definend{metacharacters}.
In place of \mbox{`\produces'}, some authors use  
\mbox{`\syntax{::=}'} or \mbox{`\syntax{:=}'}, particularly in a setting where
plain text is convenient, such as in a file used as input to
a parser generator.}

The rules specify how to derive a string in the language
from the starting nonterminal, here \syntax{<sentence>}.
Below is an example of this process.
{\setlength{\productionpadding}{0em} %temp drop extra padding around symbols
(Note that \mbox{`$\produces$'} is used in rules 
while \mbox{`$\derives$'} is used in derivations.
Read \mbox{`\derives'} aloud as ``derives'' or ``expands to.'')} 
\begin{center}
  \begin{tabular}{r@{}l}
  \syntax{<sentence>} &\derives \syntax{<noun phrase> <verb phrase>}  \\
    &\derives \syntax{<article> <adjective> <noun> <verb phrase>}  \\
    &\derives \syntax{"the" <adjective> <noun> <verb phrase>}  \\
    &\derives \syntax{"the" "young" <noun> <verb phrase>}  \\
    &\derives \syntax{"the" "young" "man" <verb phrase>}  \\
    &\derives \syntax{"the" "young" "man" <verb> <noun phrase>}  \\
    &\derives \syntax{"the" "young" "man" "caught" <noun phrase>}  \\
    &\derives \syntax{"the" "young" "man" "caught" <article> <noun>}  \\
    &\derives \syntax{"the" "young" "man" "caught" "the" <noun>}  \\
    &\derives \syntax{"the" "young" "man" "caught" "the" "ball"}  
  \end{tabular}
\end{center}
Every derivation from this grammar starts with the same
nonterminal, \syntax{<sentence>}.
Each step yields a string that is a collection of nonterminals and 
terminals.
In the grammar given above,
all the rules have a head that is a single nonterminal, so to derive the 
next string
we pick a nonterminal in the present string
and substitute the associated rule body; sometimes we say that
we ``rewrite'' the head as the body, or ``expand'' the head to the body.

The derivation given here always substituted for the leftmost nonterminal, 
so it is a \definend{leftmost derivation},
but in general we could substitute for any nonterminal.
Further, in general, we can have that a rule's head contains more than just
a single nonterminal; we will see examples at the end of this subsection.

We can represent the derivation with a \definend{parse tree}.\footnote{It 
is from where the components lie in the parse tree that we get the words 
`terminal' and `nonterminal'.}
\begin{center}
  \includegraphics{languages/asy/parsetree/parsetree000.pdf}
\end{center}
\end{example}

In examples and exercises we often use small grammars whose 
terminals and nonterminals do not have any particular meaning.
In that case, we drop the verbose notation like
`\syntax{<sentence> \produces{} <noun phrase> <verb phrase>}'
used above, in favor of 
writing nonterminals as upper case letters and terminals
as lower case letters.

\begin{example}
With this two-rule grammar 
\begin{clip}
  \syntax{S \produces{} "a"S"b" | \emptystring}
\end{clip}
we can derive the string $\str{a}^2\str{b}^2$.
\begin{displayedsteps}
  \initialstep\syntax{S}
  \derives\syntax{"a"S"b"}
  \derives\syntax{"aa"S"bb"}            
  \derives\syntax{"aa"\emptystring"bb"}
  \derives\syntax{"aabb"}  
\end{displayedsteps}
Observe that the rule for \syntax{S} is recursive.
That doesn't mean that we get stuck 
in infinite regress.
The question is not whether you could perversely 
keep expanding \syntax{<natural>} forever,
the question is whether a string has a terminating derivation. 
\end{example}

\begin{definition}
A \definend{grammar} is a four-tuple $\mathcal{G}=\sequence{\Sigma,N,S,P}$.
First, $\Sigma$ is an alphabet, the elements of which are
\definend{terminal symbols}.
Second, $N$ is a set of \definend{nonterminals} 
(or \definend{syntactic categories}), none of which are elements of $\Sigma$. 
Third, $S\in N$ is the \definend{start symbol}. 
Fourth, $P$ is a set of \definend{productions} or \definend{rewrite rules}.
\end{definition}

Neither of the sets $\Sigma$ or $N$ can contain the symbols 
{\setlength{\productionpadding}{0em} %temp drop extra padding around symbols
\mbox{`\produces'} or \mbox{`\derives'}}.
Every derivation begins with the start symbol~$S$;
we use the convention that it is the one that appears 
first in every rule set. 

As we saw with the preliminary examples,
the production rules are somethng like instructions in a program
in that they guide the evolution of
a derivation.
Here is the complete description of how they
give rise to the associated derivations.

% Each rule
% describes allowed replacments, in the course of a derivation, 
% of nonterminal symbols on the left side 
% with the strings of the rule's right side. 
Each rule has the form \mbox{`head\produces{}body'}, where
the head has consists of a single nonteminal.\footnote{%
More general definitions are possible.
One is that we could allow nonterminals in the head,
as with the rule \str{a}S\str{b}\produces\str{c}, 
%\syntax{"a"S"b"\produces{"c"}}, 
so that as one step in a derivation we could get
%\protect\syntax{"bb"T"a"S"ba"}\protect\derives\protect\syntax{"bb"T"ca"}.
\str{bb}T\str{a}S\str{ba}\derives\str{bb}T\str{ca}.
This definition allows rule heads of the form 
$\sigma_0S\sigma_1$ where $\sigma_0$ and~$\sigma_1$ are 
strings of terminals  
that provide a context
for the nonterminal~$S$, and substitutions for $S$ are only allowed in context.
(The $\sigma_i$'s could be empty.)
% Then, in each step of a derivation 
% looks like 
% \begin{equation*}
%   \tau_0\concat\sigma_0S\sigma_1\concat\tau_1
%   \derives
%   \tau_0\concat\text{body}\concat\tau_1
% \end{equation*}
% where $\tau_0$ and $\tau_1$ are concatenations of terminals and 
% nonterminals, so that
% if a substring matches the rule's head
% then we can replace it with the body, retaining the context 
% of material that surrounds the head, the $\sigma_i$'s.
\protect\label{ex:anbncnGrammar}
For example, consider
\citetext{this three-rule grammar}{Taken from \protect\url{https://en.wikipedia.org/wiki/Formal_grammar}.}:  
% in the second and third rules, the 
% head is more than just a single nonterminal.
% \begin{clip}
% \protect\syntax{S \protect\produces{} "a"BS"c" | "abc"},
S\produces{} \str{a}BS\str{c} | \str{abc},
and 
% \protect\syntax{B"a" \protect\produces{} "a"B},
B\str{a}\produces{}\str{a}B,
and
% \protect\syntax{B"b" \protect\produces{} "bb"}.
B\str{b}\produces{}\str{bb}.
% \end{clip}
In the derivation
  S 
  \derives\str{a}BS\str{c}
  \derives\str{a}B\str{abcc}
  \derives\str{aa}B\str{bcc}
  \derives\str{aabbcc}
the third step uses the second rule,
and the fourth step used the third rule.
% taking \protect\syntax{"a"B"abcc"} to be of the form 
% $\tau_0\,\text{\syntax{Ba}}\,\tau_1$, so
% that $\tau_0=\text{\syntax{a}}$ and $\tau_1=\text{\syntax{bbc}}$,
% and it rewrites \syntax{B"a"} as \syntax{"a"B}. 
% Similarly, the fourth step applies the third rule to 
% find \syntax{Bb} in the context
% of $\tau_0=\text{\syntax{aa}}$ and $\tau_1=\text{\syntax{cc}}$,
% and rewrite it as \syntax{bb}.
Grammars of this kind, called \protect\definend{context sensitive}, 
can describe more languages than the definition that
we are using.
But our definition meets our main goal, which is to convey how we can describe
languages that are constructed following rules, and besides,
our definition appears often in practice 
because it is a good blend of convenience with power. 
} 
The body is a concatenation of terminals and nonterminals (it may be empty).
Each derivation has this form,
where $\tau_0$ and $\tau_1$ are concatenations of terminals and non-terminals.
\begin{displayedsteps}
  $\tau_0\concat\text{head}\concat\tau_1$
  \derives
  $\tau_0\concat\text{body}\concat\tau_1$
\end{displayedsteps}
In words: if we find a match for the rule's head
then we can replace it with the body, retaining the context 
of material surrounding the head.

\begin{remark}
A common problem with the grammars relates to 
the following bit of C-like pseudocode that shows nested if statements. 
\begin{lstlisting}
  if ... then ... if ... then ... else ...
\end{lstlisting}
This is a ``dangling else.''
As written, we cannot tell whether the \lstinline!else! is associated
with the first \lstinline!if! or the second.
\begin{center}
  \begin{minipage}{0.4\linewidth}
    \begin{lstlisting}
      if ... 
      then ...
          if ...
          then ... 
      else ...
    \end{lstlisting}
  \end{minipage}
  \quad
  \begin{minipage}{0.4\linewidth}
    \begin{lstlisting}
      if ... 
      then ...
          if ...
          then ... 
          else ...
    \end{lstlisting}
  \end{minipage}
\end{center}
An \definend{ambiguous grammar}
is one where some strings in the language 
have two different leftmost derivations. 

This grammar for expressions of elementary algebra
\begin{grammar}
<expr> \produces{} <expr> "+" <expr>
        \alt  <expr> "*" <expr>
        \alt  ( <expr> ) |  "a"  |  "b"  | \ldots{} | "z"
\end{grammar}
is ambiguous. 
The expression \str{a+b*c} has this 
leftmost derivation
\begin{center}
\hspace{1em}\begin{tabular}{l}
  \syntax{<expr>}\derives\syntax{<expr>"+"<expr>}
  \derives\syntax{"a" "+" <expr>}                 \\ \quad
  \derives\syntax{"a" "+" <expr> "*" <expr>}          
  \derives\syntax{"a" "+" "b" "*" <expr>}          
  \derives\syntax{"a" "+" "b" "*" "c"}          
\end{tabular}
\end{center}
and this one also.
\begin{center}
\hspace{1em}\begin{tabular}{l}
  \syntax{<expr>}\derives\syntax{<expr> "*" <expr>}
  \derives\syntax{<expr> "+" <expr> "*" <expr>}    \\ \quad 
  \derives\syntax{"a" "+" <expr> "*" <expr>}  
  \derives\syntax{"a" "+" "b" "*" <expr>}  
  \derives\syntax{"a" "+" "b" "*" "c"}          
\end{tabular}
\end{center}
The two give different parse trees.
\begin{center}
  \includegraphics{languages/asy/parsetree/parsetree002.pdf}
  \hspace{2.5em}
  \includegraphics{languages/asy/parsetree/parsetree003.pdf}
\end{center}
Here is an unambiguous grammar.
With it we can derive \str{a+(b*c)} but not
\str{a+b*c}.
\begin{grammar}
<expr> \produces{} <expr> "+" <term>  |  <term> | 

<term> \produces{} <term> "*" <factor>  |  <factor>  

<factor> \produces{} ( <expr> ) |  "a"  | "b" | \ldots{} | "z"
\end{grammar}
\end{remark}

\begin{definition}
The \definend{language derived from a grammar} 
is the set of strings of terminals having derivations
beginning with the start symbol.
\end{definition}

\begin{example}
Any finite language is derived from a grammar.
This one gives the language of all length~$2$ bit strings.
\begin{clip}
  \syntax{S \produces{} "00" | "01" | "10" | "11"}
\end{clip}
This slightly more sophisticated approach gives the length~$3$ bit strings.
\begin{clip}
  \syntax{A \produces{} "0"B | "1"B}

  \syntax{B \produces{} "0"C | "1"C}

  \syntax{C \produces{} "0" | "1"}
\end{clip}
\end{example}

\begin{example}
This grammar
\begin{clip}
  \syntax{S \produces{} "a"S"b" | \emptystring}
\end{clip}
describes the set
of strings of \str{a}'s followed by \str{b}'s, with the 
same number of each, $\lang{L}=\set{\str{a}^n\str{b}^n\suchthat n\in\N}$.
Here is the derivation of \str{aabb}:
\syntax{S}\derives \syntax{"a"S"b"}\derives\syntax{"aa"S"bb"}
\derives\syntax{"aa"\,\emptystring\,"bb"}. 
\end{example}

Our purposes are best served by a variant of the above grammars,
called \definend{Backus-Naur form, BNF}.
BNFis not able to describe as many languages as the grammars
described in the prior subsection.
But it is very convenient and is powerful enough to describe the 
computer languages widely used today such as C, Java, and Scheme. 
Because of this combination of convenience and power, it is widely used.

\begin{example}
This is a BNF description for strings that denote natural numbers.
\begin{grammar}
  <natural> ::= <digit>

\end{grammar}

       &\derives\syntax{32<natural>}  \\

EBNF

\begin{example}
This is a grammar for real numbers, positive or negative, 
having a finite decimal part.
Take the rules for \syntax{<natural>} from the prior example.
\begin{grammar}
  <start> \produces{}  "-"<fraction>
        \alt "+"<fraction> 
        \alt <fraction>                

  <fraction> 
     \produces{} <natural> 
        \alt <natural>.<natural>     
\end{grammar}
Here is a derivation for \syntax{"2.718"}. 
It is a rightmost derivation.
\begin{displayedsteps}
  \initialstep\syntax{<start>}
  \derives\syntax{<fraction>}
  \derives\syntax{<natural>.<natural>}            
  \derives\syntax{<natural>.<digit><natural>}
  \derives\syntax{<natural>.<digit><digit><natural>}  
  \derives\syntax{<natural>.<digit><digit><digit>}
  \derives\syntax{<natural>.<digit><digit>"8"}  
  \derives\syntax{<natural>.<digit>"18"}
  \derives\syntax{<natural>."718"}

Here is a more life-sized example.
Representing \citetext{time is a complicated engineering problem}{%
One example of a complication, among many, is leap seconds.
The Earth is constantly undergoing a deceleration caused by the 
braking action of the tides. 
The average deceleration of the Earth is roughly $1.4$ milliseconds per day 
per century, although the exact number varies from year to year. 
To ensure that 
atomic clocks and the Earth's rotational time do not differ  
by more than $0.9$ seconds,
occasionally an extra second is added to civil time. 
This leap second can be either positive or negative depending on the Earth's 
rotation\Dash on occasion there are minutes with only $58$ seconds, and on
occasion minutes with~$60$.
Adding to the confusion is that the changes in rotation are uneven and
leap seconds cannot be predicted far into the future.  
The International Earth Rotation Service publishes bulletins that
announce leap seconds with a few weeks warning. 
Thus, there is no way to determine how many seconds there will be between 
the current instant and ten years from now.
Since the first leap second in 1972, all leap seconds have been positive and 
there were 23 leap seconds in the 34 years to January, 2006.
\autocite{web:USNO}}.
One solution, specified in \citetext{RFC~3339}{\autocite{rfc3339}},
\textit{Date and Time on the Internet: Timestamps}, 
is to require strings such as
\citetext{\str{1985-04-12T23:20:50.52Z} 
and \str{1996-12-19T16:39:57-08:00}}{%
This format has a number of advantages including human readability,
that they sort reasonably (earlier times sort earlier),
simplicity (there is one basic format),
and that they include the time zone information.}.
Here is the \citetext{the grammar for timestamps}{%
Some notes: 
(1)~Coordinated Universal Time, the basis for civil time, is
often called UTC, but is sometimes abbreviated Z,
(2)~years are four digits to prevent the Y2K problem \autocite{y2k},
(3)~the only month numbers allowed are $01$--$12$ and in each month
only some day numbers are allowed,
and (4)~the only time hours allowed are $00$--$23$, minutes must 
be in the range $00$--$59$, etc. \autocite{rfc3339}}
(some nonterminals are from \cref{exer:GrammarsForSmallLangs}).
% % https://www.ietf.org/rfc/rfc3339.txt
   % date-month      = 2DIGIT  ; 01-12
   % date-mday       = 2DIGIT  ; 01-28, 01-29, 01-30, 01-31 based on
   %                           ; month/year
   % time-hour       = 2DIGIT  ; 00-23
   % time-minute     = 2DIGIT  ; 00-59
   % time-second     = 2DIGIT  ; 00-58, 00-59, 00-60 based on leap second
   %                           ; rules
   % time-secfrac    = "." 1*DIGIT
   % time-numoffset  = ("+" / "-") time-hour ":" time-minute
   % time-offset     = "Z" / time-numoffset

   % partial-time    = time-hour ":" time-minute ":" time-second
   %                   [time-secfrac]
   % full-date       = date-fullyear "-" date-month "-" date-mday
   % full-time       = partial-time time-offset

   % date-time       = full-date "T" full-time
\begin{grammar}
<date-fullyear> ::= <4 digits>

<date-month> ::= <2 digits>

<date-mday> ::= <2 digits> 

<time-hour> ::= <2 digits>

<time-minute> :: <2 digits>  

<time-second> ::= <2 digits> 

<time-secfrac> ::= "." <1 or more digits>

<time-numoffset> ::= ("+" | "-") <time-hour> ":" <time-minute>

<time-offset> ::= "Z" | <time-numoffset>

<partial-time> ::= <time-hour> ":" <time-minute> ":" <time-second> [<time-secfrac>]

\end{grammar}

\subsection{Representation}
To solve problems with a mechanism we must first represent it
in a form the mechanism can handle, then 
apply an algorithm, and finally interpret the solution,
that is, de-represent it.

We saw this with addition on a Turing machine. 
We represented the input as two natural numbers in unary,
where the number $n$ is represented by $n$-many \str{1}'s,
separated by a blank.
The output was a single natural number, represented in unary.

% \begin{example}
% The set of numbers represented in unary is
% $\lang{L}_\text{unary}=\set{\str{1}^n\suchthat n\in\N}$.
% The notation $\str{1}^n$ means a sequence of $n$-many \str{1}'s,
% including that $\str{1}^0=\emptystring$.
% \end{example}

There is nothing sacred about that representation; sometimes
representing $n$ with $n+1$~many \str{1}'s is more convenient,
since representing zero with the empty string can be awkward.
Another obvious representation for natural numbers is binary notation.

To represent a sequence of numbers we could use a bit string of unary
representations separated by \str{0}'s, so that 
the sequence $\sequence{2,1,3}$ becomes
$\str{11010111}$. 
Another possiblity is to put the numbers as 
powers of primes, so that the sequence $\sequence{2,1,3}$ is represented by 
the single number $2^23^15^3=1500$, in whatever way we have chosen to 
represent that number.

\begin{example}
The \definend{Shortest Path Problem} is to find the cheapest path through a
graph where each edge has a cost.
For instance, we could start with this graph and look for 
the path between $a$ and~$f$ of smallest total cost.
\begin{center}
  \includegraphics{languages/asy/dijkstra.pdf}
\end{center} 
An algorithm that solves this problem inputs a member of 
this set.
\begin{equation*}
  \lang{L}_\text{SP}=\set{\sequence{\mathcal{G},p}\suchthat
                \text{$\mathcal{G}$ is a graph and $p=\sequence{n_\text{start},n_\text{end}}$, where $n_\text{start}$, $n_\text{end}$ are nodes}}
\end{equation*}
To make a complete analysis we must also specify 
the representation of the graph and of the nodes.
The nodes might be integers, represented in binary, 
then inputted as bit strings. 
The graph could be an ordered pair, $\sequence{\mathcal{N},\mathcal{E}}$,
of a set of nodes and a set of edges, where each edge is a set of two nodes. 
In short, languages can be complicated.

The above does not satisfy the definition of
a language, since $\lang{L}_\text{SP}$ is not a set of strings but
is instead a set of pairs.
We could satisfy the definition by recasting each 
$\sequence{\mathcal{G},p}\in\lang{L}_\text{SP}$ 
as the string with character
`\str{<}', followed by the string representation of $\mathcal{G}$, then a 
comma `\str{,}', then the representation of~$p$,
and finally closing with `\str{>}'.
However we won't bother; when communicating with people instead of
machines we often choose conceptual clarity over syntactic purity.
\end{example}

When we solve a problem the algorithm is tied to the 
representation of the input and output, as well as the representation of 
whatever data structures tht we use for intermediate work.
For example, a person used to programming may have the reaction that unary
notation is wasteful. 
If we, say, want a routine that adds one to a number and if the input
is the number $1000$, then representing it in unary would require the 
Turing machine to take a thousand steps just to read the input, 
while in binary notation the input is $\str{1111101000}$, which 
takes only ten steps to read.
But in this chapter we are not concerned with efficiency, 
we are instead focussed on giving a convincing argument
for what can in principle be computed.
Numbers can be represented in binary but representing them in unary
makes the example of the successor function easier, so we did that.
(We will consider issues of efficiency, of what is the best possible 
representation, when we study Complexity.)

In fact, we will just use Church's Thesis.
We note that numbers and sequences, as well as other data structures such
as character strings and arrays of numbers, can be done
in Scheme, so it can be done on a computer, and hence it can be done
on a Turing machine.
Church's Thesis gets us out of this thicket.

\extra{Extended Backus-Naur form}

Many authors use an extensions of BNF.
Optional items are enclosed in metasymbols \syntax{[} and {]}.
For example:
\begin{grammar}
    <if_statement> ::=  if <boolean_expression> then
                             <statement_sequence>
                        [ else
                             <statement_sequence> ]
                        end if ;
\end{grammar}
Repetitive items (zero or more times) are enclosed in themetasymbols 
\syntax{\{} and \syntax{\}}.
For example:
\begin{grammar}
    <identifier> ::= <letter> { <letter> | <digit> }
\end{grammar}
This rule is equivalent to the recursive rule
\syntax{<identifier> ::= <letter> |
                     <identifier> [ <letter> | <digit> ]}.

Terminals of only one character are surrounded by quotes (") to distinguish them from meta-symbols.
\begin{grammar}
    <statement_sequence> ::= <statement> { ";" <statement> }
\end{grammar}
There is a grammar for EBNF written in BNF.
\begin{clip}
\syntax{syntax     ::=  { rule }}

\syntax{rule       ::=  identifier  "::="  expression}

\syntax{expression ::=  term { "|" term }}

\syntax{term       ::=  factor { factor }}

\syntax{factor     ::=  identifier |}

\syntax{                quoted_symbol |}

\syntax{                "("  expression  ")" |}

\syntax{                "["  expression  "]" |}

\syntax{                "{"  expression  "}"}

\syntax{identifier ::=  letter { letter | digit }}

\syntax{quoted_symbol ::= """ { any_character } """}
\end{clip}

\extra{Lambda Calculus and Scheme}
% See http://matt.might.net/articles/compiling-up-to-lambda-calculus/

% Jim Larson
% 1996-07-26
% This talk was given at the JPL Section 312 Programming Lunchtime Seminar.

A function accepts input and produces an output. 
Suppose we have a ``chocolate-covering'' function that produces the 
following outputs for the corresponding inputs:
% \begin{grammar}
%   \str{peanuts} &\produces  \str{chocolate-covered peanuts} \\
%   \str{rasins}  &\produces  \str{chocolate-covered rasins} \\
%   \str{ants}    &\produces \str{chocolate-covered ants}
% \end{grammar}
We can use Lambda-calculus to describe such a function.
\begin{equation*}
	\lambda x.\str{chocolate-covered $x$}
\end{equation*}
This is a \definend{lambda-expression}.

To apply the function to an argument, use the following syntax.
% \begin{equation*}
%   (\lambda x.\str{chocolate-covered $x$})\,\str{peanuts} 
%     \produces \str{chocolate-covered peanuts}
% \end{equation*}
Functions can also be the result of applying a lambda-expression, as with this ``covering function maker.''
\begin{equation*}
  \lambda y.\lambda x.\str{$y$-covered $x$}
\end{equation*}
Use this to create a caramel-covering function.
% \begin{align*}
%   (\lambda y.\lambda x.\str{$y$-covered $x$})\,\str{caramel} 
%     &\produces \lambda x.\str{caramel-covered $x$}   \\
%   (\lambda x.\str{caramel-covered $x$})\,\str{peanuts} 
%     &\produces \str{caramel-covered peanuts}
% \end{align*}
Functions can also be the inputs to other functions, as with this 
``apply-to-ants'' function.
\begin{equation*}
	\lambda f.(f)\,\str{ants}
\end{equation*}
We can feed the chocolate-covering function to the "apply-to-ants" function:
% \begin{multline*}
% 	(\lambda f.\str{$(f)$ants})\lambda x.\str{chocolate-covered $x$}  \\
%       \begin{split}
%         \hspace*{3em}
% 	&\produces (\lambda x.\str{chocolate-covered $x$})\str{ants}  \\
% 	&\produces \str{chocolate-covered ants}
%       \end{split}
% \end{multline*}

Lambda-expressions have the following syntax.
\begin{lstlisting}
	lambda-expression ::=	variable
				| constant
				| application
				| abstraction
	application ::= (lambda-expression)lambda-expression
	abstraction ::= Lvariable.lambda-expression
\end{lstlisting}
The evaluation of lambda-expression is from the application of two reduction 
rules. 
The \definend{alpha-reduction} rule says that 
we can consistantly rename bindings of variables
% \begin{equation*}
% 	\lambda x.E \produces \text{$\lambda z.\{z/x\}E$ 
%                         for any $z$ which is neither free nor bound in $E$}
% \end{equation*}
where $\{z/x\}E$ means the substitution of $z$ for $x$ for any free occurance 
of $x$ in $E$. 
The \definend{beta reduction} rule says that application of a 
lambda-expression to an argument is the consistent replacement of the 
argument for the lambda-expression's bound variable in its body:
\begin{equation*}
	(\lambda x.P)Q -> [Q/x]P
\end{equation*}
where $[Q/x]P$ means the substitution of $Q$ for $x$ for any free occurrance 
of $x$ in $P$.

The Church-Rosser Theorem states that the final result of a chain of 
substitutions does not depend on the order in which the substitutions are 
performed.

\extrasubsection{Universality of Lambda-calculus}
The Lambda-calculus is a universal model of computation, that is, 
any computation that can be expressed in a Turing machine can also be 
expressed in the lambda calculus.

To show this, here is the translation of a conditional control structure 
into lambda-calculus.
\begin{align*}
	\str{true} &= \lambda x.\lambda y.x  \\
	\str{false} &= \lambda x.\lambda y.y        \\
	\str{if-then-else} &= \lambda a.\lambda b.\lambda c.((a)b)c 
\end{align*}
Here is an application of those rules.
% \begin{multline*}
% 	(((\str{if-then-else})\str{false})\str{apple})\str{banana}  \\
%       \begin{split}
%         \qquad 
% 	&\produces (((\lambda a.\lambda b.\lambda c.((a)b)c)\lambda x.\lambda y.y)\str{apple})\str{banana}       \\
% 	&\produces ((\lambda b.\lambda c.((\lambda x.\lambda y.y)b)c)\str{apple})\str{banana}          \\
% 	&\produces (\lambda c.((\lambda x.\lambda y.y)\str{apple})c)\str{banana}  \\
% 	&\produces ((\lambda x.\lambda y.y)\str{apple})\str{banana}   \\
% 	&\produces (\lambda y.y)\str{banana}    \\
% 	&\produces \str{banana}
%      \end{split}
% \end{multline*}
Here is the translation of some data structure operations.
\begin{align*}
	\str{cons} &= \lambda a.\lambda b.\lambda c.((c)a)b   \\
	\str{head} &= \lambda x.(x)\str{true}                  \\
	\str{tail} &= \lambda x.(x)\str{false}               \\
          \\
	0 &= \lambda f.\lambda x.x    \\
	1 &= \lambda f.\lambda x.(f)x  \\
	2 &= \lambda f.\lambda x.(f)(f)x   \\
	3 &= \lambda f.\lambda x.(f)(f)(f)x    \\
        \\
	\str{succ} &= \lambda n.\lambda f.\lambda x.(f)((n)f)x  \\
	+ &= \lambda m.\lambda n.\lambda f.\lambda x.((m)f)((n)f)x   \\
	* &= \lambda m.\lambda n.\lambda f.(m)(n)f           \\
	\str{zero?} &= \lambda n.((n)(\str{true})\str{false})\str{true} \\
	\str{pred} &= \lambda n.(((n)\lambda p.\lambda z.((z)(\str{succ})(p)\str{true})(p)\str{true})Lz.((z)0)0)\str{false}
\end{align*}

Lastly, you can create recursive functions with the \definend{$Y$ combinator}.
\begin{gather*}
	Y = \lambda y.(\lambda x.(y)(x)x)\lambda x.(y)(x)x        \\
	(Y)E -> (E)(Y)E -> \cdots -> (E)\ldots (E)(Y)E
\end{gather*}
We need this to create recursive functions, such as the factorial funtion:
\begin{equation*}
	\str{fact} = \lambda n.(((\str{if-then-else})(\str{zero?})n)1)((*)n)(\str{fact})(\str{pred})n
\end{equation*}
As written, this doesn't work since \str{fact} is a free variable in its 
own definition! We need some way to bind \str{fact} to ``this function,'' 
which can be done with Y.
\begin{equation*}
	\str{fact} = (Y)\lambda f.\lambda n.(((\str{if-then-else})(\str{zero?})n)1)((*)n)(f)(\str{pred})n
\end{equation*}

\extrasubsection{From theory to programming language}
Although the lambda-calculus is powerful enough to express any program, 
this doesn't mean that you'd actually want to do so. 
After all, the Turing Machine offers an equally powerful computational basis.

The strength of the lambda-calculus is that it is easily used as a ``glue'' 
on top of a richer world of primitives. 
Its advantages as a glue are that it has a natural correspondence with the way 
that people program, and natural compilation techniques yield 
high-performance code. 
The latter comes through optimizations know as tail-call and 
continuation-passing, which are more advanced topics not covered here.

There are software engineering advantages to a language glued together 
with lambda-calculus. 
Lambda expressions can be understood locally\Dash their dependence on 
their environment is entirely through their free variables. 
Lambda expressions tend to have fewer free variables and more bound 
variables than comparable imperative code, since they do not rely as heavily 
on assignment to express the computation. 
An imperative program proceeds by altering some globally-accessible 
store of values. 
By contrast, a functional program proceeds by function application and 
the return of values. 
This eliminates large classes of errors associated with maintinaing a global store of values.

\extrasubsection{Scheme}
The Scheme programming language is essentially the lambda-calculus outlined 
above, plus these
\begin{itemize}
\item
    The ability for a lambda-expression to bind several arguments at once.
\item
    A rich set of constants, so numbers, arithmetic, data structures, etc., don't have to be built out of thin air.
\item
    Primitive control constructs, so control operations don't have to be built out of thin air.
\item
    An assignment operation, should it be necessary.
\item
    An environment of defined names, to allow for interactive use, redefinition, and recursive definitions without using the $Y$ combinator.
\item
    A library with I/O operations to connect programs to the outside world. 
\end{itemize}

In Scheme, programs look like data structures - both are built of lists. A list looks like:
\begin{equation*}
	(\str{elt1}\ \str{elt2}\ ...\ \str{eltn})
\end{equation*}
where each element is either an atom (number or symbol), or another list.

Expressions from the lambda-calculus are translated as follows:
% \begin{align*}
% 	\lambda x.M  &\becomes  \text{\codeinline!(lambda (x) M)!} \\
% 	(M)N  &\becomes  \text{\codeinline!(M N)!}
% \end{align*}
In addition, Scheme allows lambda expressions and function applications of 
more than one argument.
\begin{lstlisting}
(lambda (a b c) (+ a (* b c)))
\end{lstlisting}
The define syntax binds names to values within the local environment:
\begin{lstlisting}
(define pi 3.14159265)
(define fact
    (lambda (n)
        (if (zero? n)
        1
        (* n (fact (- n 1))))))
(define alpha (sin (/ pi 180)))
\end{lstlisting}
Some Scheme constructs are `syntactic sugar', that is, 
expressions that can be translated into expressions in terms of more 
primitive operators. 
The \codeinline!let! construct allows initialization and binding of 
local variables so that this
\begin{lstlisting}
(let ((x1 E1)
      (x2 E2)
      (x3 E3))
      ...body... )
\end{lstlisting}
is equivalent to this.
\begin{lstlisting}
((lambda (x1 x2 x3) ...body... )
E1
E2
E3)
\end{lstlisting}
% Definition of a function can be done without an explicit lambda-expression
% \begin{lstlisting}
% 	(define (f x y z)	=>	(define f
% 	  ...body...)			  (lambda (x y z)
% 					    ...body...))
% \end{lstlisting}

\extrasubsection{Standard idioms in Scheme}
Where a conventional block-structured imperative language like C or Pascal 
would write
\begin{lstlisting}
begin
    x := 1;
    y := 2 * some_global_var;
    z := some_function();
    ...body using x, y, and z...
end
\end{lstlisting}
Scheme would instead use the let syntax to bind local variables.
\begin{lstlisting}
(let ((x 1)
    (y (* 2 some-global-var))
    (z (some-function)))
    ..body using x, y, and z...)
\end{lstlisting}
As we see above, the \codeinline!let! construct is just the stylized use of 
lambda and a function application to create an environment for the body 
where the local variables are bound to their values. 
Note that this style of programming requires the local variables to be 
initialized before use.

Scheme downplays iterative constructs such as \codeinline!do!, preferring 
recursive function calls. 
A special optimization called tail-recursion produces compiled code 
that is equivalent to a loop.
\begin{lstlisting}
(define (new-fact n)
    (define (iter n a)
    (if (zero? n)
        a
        (iter (- n 1) (* n a))))
    (iter n 1))
\end{lstlisting}
Compare this to the equivalent C function:
\begin{lstlisting}
int
new_fact(int n)
{
    int a = 1;
    while (n != 0)
        a *= n--;
    return a;
}
\end{lstlisting}
Note that the loop in the C version cannot be understood on its own\Dash in 
order to see what \codeinline!n! and \codeinline!a! are we have to 
see the entire function, while in the Scheme version, the 
\codeinline!iter! function can be lifted out of the \codeinline!new-fact! 
function and understood on its own\Dash it has no free variables! 
This may not seem too important for a toy example like this, but as the 
size of the function and the complexity of the loop scales up, 
this kind of modularity can be important.

Although it may seem unnecessary and clumsy to define a new function every 
time you need a loop, some common uses can be turned into functions 
themselves. 
For instance, a common operation in Scheme is the act of taking a 
list and applying a function to each of the elements, forming a new list of 
the results.
\begin{lstlisting}
(define (list-of-squares l)
    (define (iter l)
        (if (null? l)
            (quote ())
            (cons ((lambda (x) (* x x)) (car l)) (iter (cdr l)))))
    (iter l))
\end{lstlisting}
This kind of iteration is idiomatic, so we can capture it in a function:
\begin{lstlisting}
(define (map f l)
    (define (iter l)
        (if (null? l)
            (quote ())
            (cons (f (car l)) (iter (cdr l)))))
        (iter l))

(define (list-of-squares l)
    (map (lambda (x) (* x x)) l))
\end{lstlisting}
We could produce this program in C as well, using the technique of passing 
pointers to functions as arguments to other functions. 
However, there are some features of C that make this difficult. 
Suppose we want a function to do an affine transformation $Ax + B$ on a 
list of numbers, with A and B as parameters to the function. 
In C we have to write this.
\begin{lstlisting}
double A, B;	/* global variables */
static double
affine(double x)
{
    return A * x + B;
}

List *
affinelist(double a, double b, List *l)
{
    A = a;
    B = b;
    return map(&affine, l);
}
\end{lstlisting}
Since in C, the map function accepts only a function pointer, 
the transformation parameters have to be held in some static location for 
the affine function to find them. This prevents the code from being 
reentrant\Dash only one call to affinelist can be active at a time.

Pascal allows functions to be declared within a block, and to have access 
to all the variables visible within that block. 
In a `block-structured' variation of C would could do the following:
\begin{lstlisting}
List *
affinelist(double a, double b, List *l)
{
    double
    affine(double x)
    {
        return a * x + b;
    }
    return map(&affine, l);
}
\end{lstlisting}
This allows the function to be re-entrant. 
But Scheme allows us even more freedom in the use of these local 
functions\Dash they can persist even after the return of the parent function! 
The variables bound by the parent function are still accessible to the local 
functions, and only by them, in effect creating an opaque object with the 
local functions as the methods for accessing its state. 
This gives us a way to do object-oriented programming with higher-order 
functions in Scheme.

Suppose we want to create an object with state variables svN and methods 
methodN.
\begin{lstlisting}
(define (make-object sv1 sv2 ... svN)
    (lambda (mesg)
        (cond ((eq? mesg (quote method1)) (lambda args1 body1))
               ((eq? mesg (quote method2)) (lambda args2 body2))
                 ...
               ((eq? mesg (quote methodM)) (lambda argsM bodyM))
               (else (error "Unknown method for object")))))

(define (method1 obj args1) ((obj (quote method1)) args1))
    ...
\end{lstlisting}
So an object is a procedure which accepts a message and dynamically 
returns a procedure which will handle that message. 
Each procedure has access to the state variables which were used to create 
the object. 
Multiple instances are created through multiple invocations of the 
\codeinline!make-object! function. 
Class structure and inheritance can be accomplished through delegation. 
So use of higher-order functions can implement object-oriented code in a 
natural way.

Here are some advantages of a lambda-calculus-based programming language.
\begin{itemize}
\item
    A clean mathematical basis. The formal specification of the language doesn't need to refer to a machine or compiler.
\item
    Many common programming idioms have a natural representation.
\item
    Advanced programming through higher-order functions.
\item
    Direct correspondence with advanced mathematical objects such as functionals.
\item
    Efficient machine implementation.
\item
    Programs are more modular\Dash they can be understood and analyzed locally. 
\end{itemize}

There are some disadvantages too.
\begin{itemize}
\item
    Real-world implementations are not as good as they could be.
\item
    The model of computation provided by the language is far removed from the realities of the underlying machine. This can be both good and bad.
\item
    Things that are simple in other languages tend to be hard in Scheme, yet some simple Scheme tricks are hard to do in other languages.
\item
    Programming with full lambda-calculus requires a garbage collector in the runtime system. This entails
        a more complicated runtime system than Fortran or C, 
        difficulty in linking with code compiled from another language, and 
        complications for real-time or interactive use. 
\end{itemize}
